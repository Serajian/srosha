Branch: `feat/api-key`

# Summary

از پنج جدول، `api_keys` تنها یکی بود که هیچ domain ای نداشت — migration و query
داشت و بس. حالا دارد، به‌علاوهٔ repository و لایه‌ای که می‌داند یک کلید چه شکلی
است.

## چرا احراز هویت یک lookup است، نه یک مقایسه

معمولاً دو مرحله است: با username ردیف را پیدا کن، بعد password را با hash ذخیره‌شده
مقایسه کن. اینجا **username وجود ندارد** — کلید هم شناسه است هم راز:

```
key  →  SHA-256  →  ردیف را با همین hash پیدا کن
                    پیدا شد؟ احراز هویت شد
```

به همین دلیل `bcrypt` غلط است: salt جداگانه برای هر ردیف یعنی برای یافتن ردیف باید
کل جدول خوانده شود. SHA-256 قطعی است پس ایندکس کار می‌کند، و یک کلید ۲۵۶ بیتی
تصادفی اصلاً حدس‌زدنی نیست تا کندی چیزی بخرد.

## سه لایه، هرکدام یک کار

```
adapter/auth   ──  می‌داند کلید چه شکلی است: پیشوند، طول، SHA-256
      ↓  hash
source.Authenticator  ──  «کلید زنده یعنی این منبع» + EnsureActive
      ↓                     ↑ source.KeyRepository
db/postgres/apikey.go  ──  فقط ردیف را پیدا می‌کند
```

**`Key` در پکیج `source` است، نه پکیج خودش.** چون query ای که احراز هویت می‌کند یک
`Source` برمی‌گرداند (JOIN، تا مسیر داغ دو round trip نشود)، و در این مخزن **هیچ
domain ای domain دیگری را import نمی‌کند** — این را چک کردم، واقعاً برقرار است. یک
پکیج `apikey` مجبور بود `source` را import کند.

## یک خطا، برای هر سه حالت

```
کلید ناشناخته  ┐
کلید باطل‌شده   ├─→  هر سه در WHERE حذف می‌شوند  →  no row  →  «invalid credentials»
کلید منقضی     ┘
```

اگر جواب‌ها فرق کنند، به هرکسی که دارد حدس می‌زند گفته‌ایم کدام رشته‌اش روزی واقعی
بوده. تستش دو پیام را واقعاً با هم مقایسه می‌کند، نه فقط نوع خطا را.

**ولی منبع معلق فرق دارد:** کلید درست است و حساب خاموش — `Forbidden` نه
`Unauthenticated`. مشتری‌ای که «invalid credentials» می‌شنود کل outage را صرف چرخاندن
کلیدی می‌کند که هیچ‌وقت مشکل نبوده.

## `RecordUse` عمداً جدا از `Authenticate` است

`last_used_at` دفترداری است. اگر داخل `Authenticate` بود، شکست یک UPDATE می‌توانست
یک درخواست معتبر را رد کند. حالا دو فراخوانی جداست و صدازننده تصمیم می‌گیرد — و تنها
جواب درست، لاگ کردن و ادامه دادن است.

تستی هست که ثابت می‌کند `Authenticate` اصلاً `Touch` را صدا نمی‌زند.

## فرمت کلید

```
srosha_  +  base64url(32 بایت تصادفی)  =  ۵۰ کاراکتر
```

پیشوند دو کار می‌کند: ابزار اسکن راز می‌تواند یک الگو یاد بگیرد، و آدمی که یک رشتهٔ
ناشناس در لاگ می‌بیند می‌فهمد چیست.

`Scheme.Parse` شکل را **قبل از هر تماس با دیتابیس** چک می‌کند، پس یک هدر آشغال هیچ
query ای هزینه ندارد — و با همان خطای کلید ناشناخته رد می‌شود، وگرنه API یک probe
برای فرمت ما می‌شد.

## `ListAPIKeysBySource` اضافه شد

چرخش کلید طبق ARCHITECTURE این است: «دومی را صادر کن، بگذار جابه‌جا شوند، اولی را
باطل کن». برای «اولی را باطل کن» مشتری باید بتواند ببیند کدام کدام است. بدون این
query، باطل کردن یعنی حدس زدن.

`key_hash` انتخاب **نمی‌شود** — هیچ چیز در این مسیر مقایسه نمی‌کند، و hash ای که از
سرویس بیرون برود همان چیزی است که کسی با یک رشتهٔ پیداشده لازم دارد تا بفهمد مال
ماست.

کلیدهای باطل‌شده برمی‌گردند: بعد از یک حادثه، اولین سؤال دربارهٔ همان ردیف باطل‌شده
است.

## `Touch` و `Revoke`، دو جواب متضاد به صفر ردیف

| | صفر ردیف یعنی |
| --- | --- |
| `Touch` | داخل پنجره بوده — **موفقیت**، و در واقع حالت عادی |
| `Revoke` | از قبل باطل بوده یا هرگز نبوده — **خطا**، چون اپراتور باید بداند |
