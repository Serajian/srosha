Branch: `feat/admin-panel`

# Summary

هستهٔ پنلِ ادمین، زیرِ صفحه‌ها. پنج قدم که هیچ‌کدام صفحه‌ای ندارند و بدونشان
هیچ صفحه‌ای ممکن نیست: وضعیتی که «رد شد» را از «هنوز ندیده‌ام» جدا می‌کند، جایی
برای نوشتنِ دلیل، و use case ای که تصمیم‌ها از آن رد می‌شوند.

## رد کردن یک وضعیت است، نه یک نبودن

تا امروز source دو چیز داشت: `is_active` که تصمیم می‌گیرد و `approved_at` که
سابقه است. sourceـی که اپراتور رد کند دقیقاً شبیه sourceـی می‌شد که یک دقیقه
پیش ثبت شده — و هر روز دوباره در صف می‌آمد.

پس `reviewed_at` اضافه شد و `review_note` کنارش. چهار حالت از ترکیبِ سه ستون
درمی‌آید:

```
منتظر               f   —   —
تأیید شده           t   ✓   ✓
رد شده              f   —   ✓
تأیید و بعد خاموش   f   ✓   ✓
```

صف شد `reviewed_at IS NULL`، و `sources_unapproved_idx` که برای صفی ساخته شده
بود و هیچ‌وقت خواننده نداشت، همان شد.

## گذارها گارد دارند، چون بدونشان حالتِ پنجم می‌سازند

مرورِ اولین قدم دو سوراخ پیدا کرد که خودم ندیده بودم. `Restore` روی sourceـی که
رد شده بود، آن را فعال می‌کرد بدونِ اینکه «تأییدشده» ثبت شود — حالتی که در جدول
نیست. و `Refuse` روی sourceـی که از قبل تأیید شده بود، از «معلق» قابلِ تشخیص
نبود.

مرورِ نهایی سومی را پیدا کرد: `Suspend` هیچ گاردی نداشت، پس روی sourceـی که
هرگز بررسی نشده بود ردیفی می‌ساخت **دقیقاً مثلِ یک ردِ بدونِ دلیل** — و صفحهٔ
مشتری می‌نوشت «این source تأیید نشد.» و بعدش هیچ. همان چیزی که `review_note`
برای جلوگیری‌اش اضافه شده بود.

حالا هر سه گارد دارند و خطا برمی‌گردانند.

## دلیل در دو جا نوشته می‌شود، عمداً

`review_note` روی source همان است که مشتری می‌خواند، و با تصمیمِ بعدی بازنویسی
می‌شود. پس `audit_log` ستونِ `note` گرفت: کپی، نه join — همان استدلالی که
`notifications.source_name` در کامنتش دارد. یک سال بعد، دلیلِ ردِ اول باید هنوز
خواندنی باشد.

## Operators از Sources جداست

`Sources` در خطِ اولِ خودش می‌گوید چیست: *what a customer does with the things
they own*. اپراتوری که روی sourceِ کسِ دیگری کار می‌کند همان caller نیست —
نقش را چک می‌کند نه مالکیت را. یک type برای هر دو یعنی هر متد باید بداند دو
جور caller دارد، و آن `if` جایی است که یک روز اشتباه نوشته می‌شود.

هر متد اول نقش را چک می‌کند و بعد چیزی می‌خواند، و عملیاتِ ردشده **هیچ ردیفِ
audit نمی‌نویسد** — اعتبارسنجی قبل از gate است، نه داخلش.

## آدم‌ها مالِ super_admin اند

سه نقش داشتیم و `IsOperator()` دو تای آخر را یکی می‌کرد. پنل اولین جایی است که
باید فرق کنند: `admin` کارهای روزمره را می‌کند، و عوض کردنِ نقش و بستنِ حساب
فقط `super_admin`.

خواندنِ فهرست هم محدود است، نه فقط نوشتن. `admin` صفحه‌ای ندارد که آن فهرست را
نشانش دهد، و اگر use case اجازه می‌داد، تنها چیزی که بینِ او و ایمیلِ همهٔ
مشتری‌ها می‌ماند یک خطِ routing بود.

**و کسی نمی‌تواند آخرین در را از داخل قفل کند:** `super_admin` نه نقشِ خودش را
پایین می‌آورد نه حسابِ خودش را می‌بندد. وگرنه برگشتن فقط با SQL دستی است — همان
وضعیتی که این پنل برای پایان دادنش نوشته شد.

## اپراتور پیام‌ها را می‌بیند، نه محتوایشان را

`notifications` متنِ پیام را دارد و `deliveries` آدرسِ گیرنده را. اپراتور هیچ‌کدام
را نمی‌بیند، و این دو بار قفل شده:

- query هرگز `title` و `body` را select نمی‌کند
- `OperatorDelivery` فیلدی برای آدرسِ کامل ندارد، فقط `MaskedAddress`

ماسک در use case است نه در SQL — «adapter فراداده می‌دهد، core تصمیم می‌گیرد».
و آستانه دارد: زیرِ هشت کاراکتر هیچ‌چیز نشان داده نمی‌شود، حتی طول. اولین نسخه
همیشه چهار کاراکتر نشان می‌داد، که برای یک chat id ــِ شش‌رقمی صد حالت باقی
می‌گذاشت — ماسک نبود، شکلِ ماسک بود.
