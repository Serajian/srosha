# Summary

**تنها بخشی از قراردادِ srosha که در پروسهٔ مشتری اجرا می‌شود، حالا نوشته شده.**

در طراحیِ SDK عمداً بیرون گذاشته شد و در سه جا ثبت شد که نیست: spec،
`sdk/go/README.md` و doc comment ــِ `Webhooks.Register`. هر سه‌تا جایگزین شدند.

نبودنش یعنی هر مشتری خودش HMAC می‌نوشت — و آنچه معمولاً فراموش می‌شود مقایسهٔ
زمان‌ثابت و ردِ timestamp کهنه است. اولی نشتِ اطلاعات، دومی replay.

# قرارداد از قبل کامل بود

هیچ تصمیمی لازم نبود. سرور همه‌اش را دارد:

```
X-Srosha-Signature   v1=<hex ــِ hmac-sha256>
X-Srosha-Timestamp   ثانیهٔ unix
امضا روی            <timestamp> "." <body>
```

و `const.go` ــِ notifier خودش می‌گوید چرا این‌ها ثابت‌اند نه پیکربندی:

> They are this service's public contract with every source that verifies a
> signature

# ترتیبِ بررسی‌ها، و چرا

```
۱  سرصفحه‌ها هستند؟
۲  امضا می‌خواند؟        ←  زمان‌ثابت
۳  کهنه نیست؟
۴  بدنه را decode کن
```

**۳ بعد از ۲ است، نه قبلش.** تا وقتی امضا تأیید نشده، timestamp مالِ مهاجم است
نه srosha؛ بررسیِ کهنگی رویش چیزی نمی‌خرد. بعد از ۲، همه‌چیز مورد اعتماد است.

و **۴ آخر است**: هیچ چیز اینجا بایتی را تفسیر نمی‌کند که احرازش نکرده. تست دارد —
بدنه‌ای که اصلاً json نیست با امضای جعلی، «امضا نمی‌خواند» می‌گیرد نه «json خراب».

# پنجرهٔ کهنگی، و اینکه دقیقاً چیست

پنج دقیقه، و در مستند صریح گفته شد که **دقیقاً همان مدتی است که یک callback ــِ
ضبط‌شده قابلِ replay می‌ماند**. هر دو جهت بررسی می‌شود: ساعت می‌تواند جلو هم
باشد، و timestamp ــِ جلوتر از ما به همان اندازه نشانهٔ مشکل است.

# تله‌ای که فقط با خواندنِ هر دو طرف پیدا شد

callback وضعیت را **بزرگ** می‌نویسد:

```
سرور     "SENT" · "NOT_REACHABLE"
SDK      "sent" · "not_reachable"
```

دست‌نخورده رد می‌شد، `d.Status == srosha.StatusSent` **هرگز درست نمی‌شد** و هیچ
خطایی هم نبود. تبدیل انجام می‌شود و تست دارد.

# تستی که هر دو نیمه را با هم اجرا می‌کند

`internal/adapter/notifier/contract_test.go`: سرور با کدِ واقعیِ خودش امضا
می‌کند، SDK با کدِ واقعیِ خودش بررسی می‌کند، و هیچ کدِ مشترکی بینشان نیست.

**و ثابت شد که drift را می‌گیرد** — هر سه‌تا عمداً شکسته شدند:

```
جداکنندهٔ "." → ":"       →  the SDK could not verify what we signed
X-Srosha-Signature عوض    →  nothing arrived under "X-Srosha-Signature"
lowercase در SDK حذف       →  Status:SENT
```

مثلِ تستِ credential ها، فقط به این دلیل ممکن است که SDK نمی‌تواند سرور را
import کند ولی سرور می‌تواند SDK را.

# `Verify` یک تابع است، نه یک handler

در طراحی صریحاً یک `http.Handler` رد شد چون SDK را به یک framework گره می‌زند.
ولی `http.Header` گرفته می‌شود — کتابخانهٔ استاندارد است نه framework، حالتِ
حروف را خودش حل می‌کند، و هر framework ای یکی می‌دهد.

# Follow-ups / Risks

- **راز هنوز بیرون از سرویس داده می‌شود.** `NOTIF_WEBHOOK_SECRETS` یک متغیرِ
  محیطی است، پس هر مشتریِ تازه یک redeploy است. همان جنسِ شکافِ پنلِ ادمین، و
  احتمالاً همان‌جا حل می‌شود.
- **نامِ سرصفحه‌ها در دو جا تعریف شده‌اند** — `notifier/const.go` و
  `sdk/go/srosha/callback_const.go`. نمی‌شود مشترکشان کرد چون SDK نمی‌تواند
  `internal/` را ببیند. تستِ متقابل همین را می‌پاید و ثابت شد که می‌گیردش.
- **`v1` تنها نسخه‌ای است که بررسی می‌شود.** یک امضای `v2` رد می‌شود، که تنها
  جوابِ امنِ ممکن است — ولی یعنی روزی که الگوریتم عوض شود، مشتری‌ها باید اول
  SDK را ارتقا دهند.
- **کلیدِ replay فقط زمان است.** srosha شناسهٔ batch را در header نمی‌فرستد، پس
  یک callback ــِ ضبط‌شده داخلِ پنجره دوباره پذیرفته می‌شود. مستند می‌گوید برای
  تشخیصِ تکراری از `delivery id` استفاده شود — که یک بار settle می‌شود و عوض
  نمی‌شود.
