Branch: `feat/grpc`

# Summary

سه فایل proto صفر بایت بودند، `buf.yaml` وجود نداشت، و `adapter/api/grpc` هشت فایل
یک‌خطی بود. حالا gateway یک سطح gRPC واقعی دارد — قرارداد، تولید کد، ترجمه،
interceptorها، handlerها، و سروری که در `registry` بالا و پایین می‌رود.

## قرارداد از domain درآمد، نه از حدس

اولین نسخهٔ proto را از ذهن نوشتم و دو جا با واقعیت نمی‌خواند:

```
FailureReason  →  نوشته بودم EXPIRED / PERMANENT / EXHAUSTED
                  domain دارد    EXPIRED / MAX_ATTEMPTS / PERMANENT / NO_SENDER

Delivery       →  created_at گذاشته بودم
                  entity اصلاً چنین فیلدی ندارد
```

هر دو اصلاح شد. یک delivery همراه پیامش ساخته می‌شود و هرگز به‌تنهایی، پس
`created_at` معنادار همان پیام است.

## `source_id` در هیچ request ای نیست

```go
// SourceID is filled from the authenticated token, never from the body. Read
// from the body it could be spoofed; here it structurally cannot.
```

این تضمین را نگه داشتیم: `toSubmitCommand(sourceID, req)` منبع را **آرگومان**
می‌گیرد و proto اصلاً جایی برایش ندارد. تستش هم همین را ادعا می‌کند.

## هر rpc، request و response خودش

`buf lint` با قواعد استاندارد این را خواست و دلیلش واقعی است: rpc ای که با یک
پیام مشترک جواب می‌دهد، **جایی برای فیلد دوم ندارد** و اولین باری که یکی لازم شود،
هر کلاینتی می‌شکند.

پس چهار پاسخِ webhook هرکدام `Webhook` را **در بر می‌گیرند** به‌جای اینکه خودش
باشند، و چهار request خالی جدا ماندند. و چون هر دو سرویس `Get` دارند و یک پکیج
proto نمی‌تواند دو `GetRequest` داشته باشد، آن دو نامِ سرویس‌دار گرفتند.

## interceptorها: چهار تا، نه چهارتای spec

```
Recovery → Logging → Errors → Auth → handler
```

**`Errors` اضافه شد.** شش handler داریم و یکی‌شان بالاخره یادش می‌رود `Status(err)`
را صدا بزند — و یادش رفتن یعنی متن خام یک خطا بیرون برود که می‌تواند نام یک ستون،
یک host یا مقدار ردشده را داشته باشد. interceptor این را ساختاری می‌کند.

**`ratelimit` حذف شد.** spec آن را داشت ولی سهمیه از قبل در core خرج می‌شود، و
عمداً فقط روی مسیر ارسال:

```
Submit    →  source.Service.Admit  →  سهمیه خرج می‌شود
Registrar →  source.Service.Load   →  خرج نمی‌شود
```

یک interceptor یعنی `Submit` دوبار خرج شود و مدیریت webhook هم یک پیام هزینه
بردارد — دقیقاً همان چیزی که جدا بودن `Admit` از `Load` برای جلوگیری‌اش نوشته شده.

## و پکیج `interceptor` حذف شد

قرار بود زیرپکیج باشد، ولی به بن‌بست خورد: interceptorها کلید context را
می‌گذارند و handlerها می‌خوانند، و `Errors` هم به `Status` نیاز دارد. هر تقسیمی
یا حلقهٔ import می‌ساخت یا یکی از این دو را جایی می‌برد که به آن تعلق ندارد.

## یک adapter، adapter دیگری را import نمی‌کند

`Auth` مستقیم `auth.Scheme` را می‌گرفت — یعنی `grpcsrv` به `adapter/auth` وصل بود.
چک کردم: این **تنها** import از adapter به adapter در کل مخزن بود، یعنی قاعده‌ای
که همه‌جا برقرار بود همین‌جا شکسته شده بود.

حالا interface را مصرف‌کننده تعریف می‌کند:

```go
// در grpcsrv، نه import از جای دیگر
type KeyScheme interface {
	Parse(presented string) (string, error)
}
```

`auth.Scheme` بدون یک خط تغییر ارضایش می‌کند و bootstrap پایینش می‌دهد. اینکه کلید
چه شکلی است و چطور hash می‌شود کاملاً آن‌طرف این خط ماند.

قاعده به `make arch-check` و `docs/CONVENTIONS.md` اضافه شد. زیرپکیج خودِ adapter
مجاز است (`db/postgres` → `db/postgres/gen`)، ولی همسایه نه.

## فقط message از سیم رد می‌شود

```
message  →  کلاینت می‌بیند
reason   →  فقط لاگ: ستون، host، provider، مقدار ردشده
```

و خطایی که `AppError` نیست، `Internal` با پیام خودمان می‌گیرد — نه متن خودش.
`TestAForeignErrorSaysNothingAboutItself` یک خطای درایور با نام کاربر دیتابیس
می‌سازد و ثابت می‌کند هیچ‌کدام بیرون نمی‌رود.

## سرور: سه لایه، مثل HTTP

اولین نسخه همه‌چیز را در `registry` گذاشته بود — listener، goroutine، کانال خطا،
`Shutdown`. یعنی registry برای gRPC کاری می‌کرد که برای HTTP نمی‌کند. اصلاح شد:

```
adapter/api/grpcsrv   →  سروری با سرویس‌ها و interceptorها، که هنوز گوش نمی‌دهد
infra/grpcserver      →  سوکت و طول عمر  (Config, New, Start, Shutdown, Addr, Err)
registry/grpcserver   →  settings → Config، Start، ثبت در tierServer
```

دقیقاً هم‌شکل `infra/httpserver` و `registry/httpserver.go`. فایل registry از ۹۱
خط به ۴۳ خط رسید و حالا همان سه کاری را می‌کند که برای db و mq و httpclient
می‌کند.

`New` جدا از `Start` است و **هیچ پورتی نمی‌گیرد**: اشتباه سیم‌کشی قبل از اشغال
پورت پیدا می‌شود. و `Start` قبل از برگشتن bind می‌کند، پس پورت اشغال یک شکست
startup است نه یک خط لاگ که پروسه از آن جان سالم به در ببرد.

`tierServer` یعنی **اول از پذیرفتن می‌ایستد**، بعد nats، بعد استخر دیتابیس.

`StopTimeout` در کانفیگ است چون یک تصمیم عملیاتی است:

```
NOTIF_APP_SHUTDOWN_TIMEOUT = 15s   ← بودجهٔ کل خاموشی
NOTIF_GRPC_STOP_TIMEOUT    = 10s   ← سهم gRPC از آن
```

اگر یک caller کند کل بودجه را بگیرد، بقیه وقت نمی‌کنند تمیز بسته شوند.

# Follow-ups / Risks

- REST جدا ماند. `CONFIG.md` می‌گوید ۸۰۸۰ = REST via grpc-gateway، و اضافه کردنش
  بعداً چیزی نمی‌شکند: annotationهای `google.api.http` گزینه‌اند و هیچ پیام یا
  سرویس تولیدشده‌ای را عوض نمی‌کنند.
- هیچ‌کس هنوز `grpcsrv.New` یا `registry.GRPCServer` را صدا نمی‌زند. سیم‌کشی
  gateway کار بعدی است، و `adapter/system/{clock,idgen}.go` هم برای آن لازم است.
- `buf breaking` هدفی ندارد تا وقتی proto ها یک بار در master بنشینند.
- `Deactivate` و `Activate` بعد از تغییر، callback را دوباره می‌خوانند تا حالت
  تازه را برگردانند — یک round trip اضافه به دیتابیس. اگر مهم شد، `Registrar`
  می‌تواند خودش webhook را برگرداند.
