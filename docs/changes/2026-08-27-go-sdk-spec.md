# چرا ماژولِ جدا، و نه مخزنِ جدا

قبل از انتخاب، وسعت اندازه گرفته شد: **فقط یک package در سرور** کدِ تولیدشده را
import می‌کند. پس جابه‌جاییِ قرارداد گران نیست.

```
یک ماژول        نسخهٔ SDK می‌شود نسخهٔ سرور
gen دوبار        دو نسخهٔ تولیدشده از یک proto در یک مخزن
مخزنِ جدا        proto باید sync شود — و drift می‌کند، با هر زبانِ تازه بدتر
ماژولِ جدا  ✓    یک مخزن، نسخه‌های جدا، drift ممکن نیست
```

# تستی که فقط این چیدمان ممکنش می‌کند

`APNsCredential` یک JSON می‌سازد. از کجا بدانیم `apns.ParseConfig` قبولش می‌کند؟

SDK نمی‌تواند سرور را import کند — جهت برعکس است. ولی **سرور می‌تواند SDK را**:

```
sdk/go        APNsCredential{…}.Config()  →  json
                        ↓
main module   apns.ParseConfig(json)      →  باید بدون خطا رد شود
```

همان درزی که بی‌صدا باز می‌شود، بسته می‌ماند. با مخزنِ جدا این تست ممکن نبود.

# دو تله که در طراحی پیدا شدند

**۱ — کدِ تولیدشده نمی‌تواند `internal/` باشد.** قاعدهٔ `internal` در Go
مسیرمحور است؛ سرور زیر `sdk/go/` نیست، پس نمی‌بیندش. تایپ‌های protobuf ناچار
عمومی می‌شوند — و عمداً به‌عنوان دریچهٔ فرار پذیرفته شدند، نه دور زده.

**۲ — `go test ./...` وارد ماژولِ تودرتو نمی‌شود.** یعنی `make prepush` امروز SDK
را **بی‌صدا رد می‌کند**. باید صریح اضافه شود.

# آنچه رد شد، و چرا

```
SendEmail / SendTelegram / …    هفت متد با بدنهٔ یکسان         ← تشریفات
تطبیق روی متنِ پیامِ خطا          شکننده، و CONVENTIONS ردش کرده
retry ــِ توکار gRPC              یک رشتهٔ JSON مبهم به‌جای ۸۰ خطِ خوانا
تأیید امضای webhook              این نسخه نه — اولین کاندیدِ بعدی
```

آن آخری یک پیامدِ امنیتی دارد و در spec صریح نوشته شده: بدون آن، هر مشتری تأیید
HMAC را دستی می‌نویسد و اشتباهش یعنی پذیرفتنِ callback ــِ جعلی.
