# Summary

سه تایپ tag ی JSON گرفتند، و بقیه عمداً نگرفتند.

```
shared.DispatchEvent    payload صف
webhook.Batch           بدنهٔ callback
webhook.Result          هر نتیجه در آن
```

## چرا entity ها tag نگرفتند

نه از سر سلیقه — چون **دام** می‌ساخت.

```go
type Delivery struct {
    ID، NotificationID، Recipient، SenderName    export
    status، attempts، lastError، ...              مخفی
}
```

`json.Marshal` فیلد مخفی را نمی‌بیند. اگر tag می‌گذاشتیم، تایپ **قابل serialize
به‌نظر می‌رسید**، کسی marshal اش می‌کرد، و خروجی بدون `status` و `attempts` بیرون
می‌آمد — بی‌صدا و بدون هیچ خطایی.

همین برای `Notification` و `Credential` و `Webhook` هم صدق می‌کند.

## و بقیه چرا نه

| تایپ | چرا |
| --- | --- |
| `shared.Message` | درون‌فرایندی؛ هر sender payload ارائه‌دهنده‌اش را خودش می‌سازد |
| `shared.Recipient` | از طریق mapper به ستون می‌رود |
| `Cursor`، `Pagination` | لایهٔ gRPC به proto نگاشت می‌کند |
| `SendError` | عمداً هرگز بیرون نمی‌رود |
| `Snapshot` ها | نگاشت دیتابیس |
| `Registration`، `Route`، `Origin`، `Request` | ورودی داخلی |
| `URLPolicy` | از config می‌آید |

## دو تصمیم ریز

`Reason` و `ProviderMessageID` هر دو `omitempty` گرفتند، چون هیچ‌وقت با هم نمی‌آیند:
یکی فقط وقتی `FAILED` است و دیگری فقط وقتی `SENT`. بدون آن، هر نتیجهٔ موفق یک
`"reason": ""` بی‌معنی حمل می‌کرد.

و نام فیلدها **در همین‌جا** تثبیت شد نه در adapter، چون قرارداد عمومی ما با مشتری
است. اگر adapter تعیینش می‌کرد، یک adapter تازه می‌توانست بی‌خبر اسم‌ها را عوض کند
و قرارداد همهٔ مشتری‌ها را بشکند. کامنت خود تایپ همین را می‌گوید.

# Follow-ups / Risks

- `DispatchEvent.Priority` از نوع `int8` است، پس روی سیم `0`/`1`/`2` می‌رود نه
  `"NORMAL"`/`"HIGH"`/`"CRITICAL"`. برای صف مشکلی نیست چون هر دو طرف مال ماست، ولی
  اگر روزی کسی آن پیام‌ها را با چشم بخواند، `MarshalJSON` لازم می‌شود.
- زمان‌ها با قالب پیش‌فرض `time.Time` یعنی RFC 3339 سریال می‌شوند. اگر قرارداد
  چیز دیگری بخواهد، باید صریح شود.
