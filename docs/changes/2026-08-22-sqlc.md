Branch: `feat/schema`

# Summary

sqlc آمد: ما SQL می‌نویسیم، sqlc کد Go تایپ‌دار می‌سازد. برعکس ORM، که struct
می‌گیرد و SQL می‌سازد.

دلیلش صرفه‌جویی در تایپ کردن نیست. sqlc هر query را **مقابل schema در
`migrations/`** چک می‌کند، پس تغییر نام یک ستون `make sqlc` را می‌شکند نه سرویس را
ساعت سه صبح. repository ها همان لایه‌ای‌اند که بی‌صدا می‌پوسند و این دقیقاً همان را
می‌گیرد.

چیزی که تولید می‌شود **domain نیست**. آن struct ها شکل جدول‌اند؛ entity ها شکل کسب و
کار. repository بینشان ترجمه می‌کند و آن ترجمه دستی می‌ماند. sqlc کدِ `rows.Scan` را
حذف می‌کند، نه لایهٔ mapping را.

## سه چیزی که پیکربندی لازم داشت

**`ID interface{}`** — sqlc دامنهٔ `ulid` را نمی‌شناخت و همهٔ شناسه‌ها را
`interface{}` تولید کرد، یعنی همان تایپ‌ایمنی‌ای که برایش آمدیم از بین رفت. override
لازم بود، و `string` انتخاب شد نه `shared.ID`: `Source.ID` هنوز در domain یک
`string` است در حالی که بقیه `shared.ID` اند، پس mapper در هر حال تبدیل می‌کند.

**`pgtype.Timestamptz` حتی برای NOT NULL** — هر `Snapshot` با `time.Time` حرف
می‌زند، پس بدون override این تبدیل در هر mapper تکرار می‌شد. حالا NOT NULL می‌شود
`time.Time` و nullable می‌شود `*time.Time`.

**پارامتر بدون cast اشاره‌گر می‌شود** — `@now` تنها به `*time.Time` تبدیل شد چون
sqlc nullability را نمی‌داند. `@now::timestamptz` صریحش می‌کند.

## مرور query به query

query ها اول از روی port ها نوشته شدند، بعد فایل‌به‌فایل مرور شدند. آن مرور ده
ایراد پیدا کرد که هیچ‌کدام کامپایل را نمی‌شکست:

### راز کمتر در حافظه

`ListCredentialsBySourceAndChannel` با `SELECT *` توکن رمزشده را هم می‌کشید، در
مسیری که فقط انتخاب می‌کند با کدام هویت بفرستیم — و `credential.Credential` عمداً
هیچ رازی ندارد. حالا دو query است: انتخاب هویت بدون راز، و `ReadCredentialSecret`
در لحظه‌ای که واقعاً قرار است فرستاده شود.

ردیف تولیدشده حالا میدان‌به‌میدان با `credential.Snapshot` یکی است.

### فیلترهایی که پیام خطا را خراب می‌کردند

`AND is_active` در query های credential و source برداشته شد. آن فیلتر «این هویت
خاموش است» را تبدیل می‌کرد به «چنین اسمی نیست»، و شاخه‌های `!c.isActive` در `Pick` و
`EnsureActive` در domain **هیچ‌وقت اجرا نمی‌شدند** — کد مرده‌ای با تست سبز.

### نوشتن‌ها به قصدشان تقسیم شدند

`notified_at` از `UpdateDelivery` بیرون آمد، و `UpdateWebhook` به چهار statement
شکست. یک `UPDATE` که همه‌چیز را می‌نویسد به دو صدا زنندهٔ متفاوت اجازه می‌دهد کار هم
را خنثی کنند:

```
source آدرس callback را عوض می‌کند
یک callback که از قبل در پرواز بود موفق می‌شود
کل ردیف را بازمی‌نویسد، با آدرس قدیمی
```

### سه مسابقه

- **دو worker یک delivery را حل می‌کنند.** `UpdateDelivery` حالا
  `AND status = 'PENDING'` دارد و `:execrows` است: دومی صفر می‌گیرد و می‌داند باخته،
  به‌جای اینکه بی‌صدا روی جواب اولی بنویسد. at-least-once یعنی این حالت واقعاً
  پیش می‌آید.
- **درخواست تکراری با یک کلید.** بین «بخوان» و «بنویس» در `submit` فاصله هست، و
  کلاینتی که timeout خورده و دوباره فرستاده دقیقاً همان چیزی است که دو درخواست را
  در آن فاصله می‌گذارد. `ON CONFLICT DO NOTHING` با `:execrows` جایگزین خطای یکتایی
  خام شد — که به کلاینت ۵۰۰ می‌داد برای حالتی که کلید وجود دارد تا آن را زیبا کند.
- **شمارش شکست‌های هم‌زمان.** `consecutive_failures` در Go خوانده و زیاد و نوشته
  می‌شد. با ۲۰ callback هم‌زمان، افزایش‌ها گم می‌شوند — و این همان شمارنده‌ای است که
  تصمیم می‌گیرد کِی یک endpoint مرده خاموش شود. حالا در SQL زیاد می‌شود.
  مقایسه با سقف در domain ماند، که قاعده را دارد و برایش تست دارد؛ بردنش به SQL یک
  منبع حقیقت دوم می‌ساخت.

### آنچه ساخته می‌شود نمی‌تواند غلط متولد شود

`status`، `attempts`، `is_active` و `consecutive_failures` از پارامتر به default
جدول رفتند. یک delivery که همان اول `SENT` ساخته شود بی‌معنی است و حالا ممکن نیست.

### و یک شرط ثبت‌شده

`ListStaleDeliveries` ابتدا `FOR UPDATE SKIP LOCKED` داشت. برداشته شد، چون قفل فقط
داخل transaction زنده است و آن transaction باید تمام مدت ارسال باز بماند. claim
کردن با `updated_at` هم بدتر است: age همان شمارندهٔ تلاش است و صفر کردنش یعنی ردیف
هیچ‌وقت تسلیم نمی‌شود.

پس در خود query نوشته شد که **این ردیف‌ها را claim نمی‌کند**: یک dispatcher امن است،
دو تا نه — و چون بازیابی مستقیم می‌فرستد، پنجرهٔ تکراری broker نجاتش نمی‌دهد.
dispatcher دوم اول یک ستون `claimed_at` می‌خواهد.

## نگهبان

`make sqlc-check` به `precommit` اضافه شد. بدون آن کسی schema را عوض می‌کند،
تولید دوباره نمی‌زند، و کد بی‌صدا کهنه می‌ماند. با اضافه کردن یک query تازه امتحان
شد: قرمز شد، و بعد از برگرداندن سبز.

## چه چیزی امتحان شد

هر ادعا مقابل postgres واقعی اجرا شد، نه فقط کامپایل:

| | |
| --- | --- |
| کلید باطل‌شده احراز هویت می‌شود؟ | نه — و hash برای سند مانده |
| touch نمونه‌برداری‌شده | اولی نوشت، دومی داخل پنجره ننوشت، بعد از پنجره نوشت |
| credential غیرفعال برمی‌گردد؟ | بله — و راز در نتیجه نیست |
| دو worker یک delivery | `UPDATE 1` بعد `UPDATE 0`، `SENT` ماند |
| درخواست تکراری با یک کلید | `INSERT 0 1` بعد `INSERT 0 0`، یک پیام |
| source بدون کلید، دو پیام | هر دو پذیرفته |
| ۲۰ شکست هم‌زمان از ۲۰ اتصال | شمارنده `20` |
| callback در پرواز روی redirect | آدرس جدید ماند |
| تعلیق source، دوباره تعلیق | `UPDATE 1` بعد `UPDATE 0` |
| ترتیب پایدار بین دو batch | نه پرش، نه تکرار |

و کد تولیدشده مقابل دیتابیس اجرا شد — ساختن، `copyfrom`، اسکن بازیابی و صفحه‌بندی.
آن تست موقتی بود و پاک شد.

# Follow-ups / Risks

- کد تولیدشده commit می‌شود. اگر نسخهٔ sqlc کسی فرق کند، خروجی می‌تواند فرق کند و
  `sqlc-check` قرمز شود بدون اینکه چیزی خراب باشد. قفل کردن نسخه انجام نشده.
- `ReadNotificationByIdempotencyKey` با `SELECT *` کل `body` و `metadata` را
  می‌کشد، در حالی که use case فقط `ID` و `EffectivePriority` و `WasDowngraded()` را
  می‌خواهد — و آن مسیر، مسیر تلاش مجدد است. درستش یک تایپ سبک‌تر در domain است که
  هنوز ارزشش را ندارد.
- `internal/adapter/db/postgres/query.go` هنوز یک stub خالی است و با آمدن sqlc
  احتمالاً بی‌مصرف شده.
- هیچ repository ای هنوز نوشته نشده. کد تولیدشده تا آن موقع مصرف‌کننده ندارد.
- `sqlc vet` صدا زده می‌شود ولی خطایش نادیده گرفته می‌شود، چون قاعده‌ای برایش تعریف
  نشده. یا قاعده بنویسیم یا خطش را برداریم.
- `UpdateSource` مقدار `default_addresses` را یکجا می‌نویسد، پس دو ویرایش هم‌زمان
  روی دو کانال متفاوت یکی دیگری را پاک می‌کند. همان محرک jsonb که در گزارش migration
  ثبت شد.
