# کاری که با «پنلِ ادمین» شروع شد و چیزِ دیگری از آب درآمد

اولش قرار بود ادمین source ثبت کند و کلید بدهد. وسطِ گفت‌وگو عوض شد:

> «می‌خواهم admin ثبت نکند — هر source خودش بیاید ثبت کند»

و این **مسئلهٔ اصلی را وارونه کرد**: سؤالی که کلِ این کار برایش شروع شده بود —
«کلید چطور به مشتری برسد» — دیگر جواب ندارد، چون دیگر سؤال نیست. خودش می‌سازدش.

# و تجزیه شد، چون یک چیز نبود

```
۱  پورتالِ مشتری        عمومی        ← این spec
۲  پنلِ ادمین           خصوصی
۳  اشتراک و پرداخت      روی ۱ سوار می‌شود
```

فازِ ۳ عمداً آخر است: تا مشتریِ واقعی نباشد، هر تصمیمی دربارهٔ طرح و قیمت حدس
است.

# تفکیکی که همه‌چیزِ بعدش را ساده کرد

`user` و `source` تا اواسطِ گفت‌وگو یک چیز بودند. جدا که شدند:

```
یک جدولِ users        اپراتور و مشتری، با ستونِ role
یک جریانِ ورود        یکی، نه دو تا
یک جدولِ session      همان
```

داشتم به سمتِ **دو جدولِ حساب** می‌رفتم. جمع شدنشان یک جریانِ ورودِ دوم و یک
دستهٔ باگِ دوم را حذف کرد.

# سه تصمیمی که مسئله را حل کردند، نه دور زدند

## بدونِ رمز، چون اولین کاربر باید دستی ساخته شود

hash ــِ argon2 را نمی‌شود در SQL دستی نوشت. **ایمیل را می‌شود.** پس OTP — و
همان جریان برای اپراتور و مشتری کار می‌کند.

و OTP **مستقیم از خودِ باینری** می‌رود، نه از صفِ srosha: وگرنه روزی که سرویس
بشکند، هیچ‌کس نمی‌تواند وارد شود تا تعمیرش کند.

## تأیید حذف شد، و یک قاعده جایش نشست

سؤال شد چرا اصلاً باید ادمین تأیید کند. جوابِ واقعی این بود که source ــِ تازه
از **هویتِ ما** می‌فرستد:

```go
the source registered nothing at all  ->  ours
```

یعنی حسابی که یک دقیقه پیش ساخته شده، می‌تواند از باتِ srosha اسپم بفرستد.

ولی این را **تأیید حل نمی‌کند، یک قاعده حل می‌کند**:

```
sources.may_use_shared_sender = false
      ↓
تا وقتی باتِ خودش را ثبت نکرده، هیچ چیز نمی‌فرستد
```

بارِ اسپم از ما به خودِ اسپمر منتقل می‌شود. و فردا همین پرچم می‌شود چیزی که یک
**طرحِ پولی روشنش می‌کند** — از یک بدهی به یک ویژگیِ فروختنی.

## «غیرفعال کردنِ user یعنی چه؟» — و یک مسئله که حل نشد، منحل شد

پرسیده شد، و معلوم شد **یک کلمه دو کار می‌کرده**:

```
                        وارد شود   بفرستد
اپراتور می‌رود           نه         —
مشتری سوءاستفاده کند     شاید       نه، فوراً
مشتری پول نداده (فازِ ۳)  بله        نه
```

سطرِ سوم **عکسِ** سطرِ دوم است. یک آبشار بینشان، فازِ ۳ را غیرممکن می‌کرد.

پس دو اهرمِ مستقل، و هیچ آبشاری. آن سؤالی که پرسیده بودم — «روشن کردنِ دوبارهٔ
user چه می‌کند» — کلاً از بین رفت.

# بازبینیِ خودم، دو تناقض

```
«فقط super_admin کاربر می‌سازد»   ولی مشتری خودش را می‌سازد
                                  → super_admin ستونِ role را کنترل می‌کند، نه ردیف را

ثبت‌نام و ورود دو جریانِ جدا       ثبت‌نام می‌گوید «قبلاً هست»، ورود می‌گوید «کد رفت»
                                  → از تفاوتشان می‌شود فهمید چه کسی حساب دارد
                                  → یک جریان شد؛ چیزی برای لو دادن نماند
```

دومی مهم بود چون **قولی که خودِ spec چند خط بالاتر داده بود را نقض می‌کرد**.
