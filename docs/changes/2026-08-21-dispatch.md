# Summary

`usecase/dispatch.go` نوشته شد: مصرف یک event، ارسال، و ثبت نتیجه. با این، مسیر
کامل «ثبت تا ارسال» در هسته بسته شد و بدون هیچ زیرساختی تست می‌شود.

## قرارداد

```go
Handle(ctx, e shared.DispatchEvent, attempt int) error
```

`nil` یعنی broker کارش با این event تمام است — چه فرستاده شد چه برای همیشه شکست
خورد. خطا یعنی دوباره بیاورش.

`attempt` از broker می‌آید نه از ما. اگر خودمان می‌شمردیم، تلاشی که worker وسطش
می‌میرد هیچ‌وقت شمرده نمی‌شد و آن پیام تا ابد retry می‌کرد.

## هشت مسیر خروج

```
delivery نیست              ack + لاگ. تلاش دوباره چیزی را درست نمی‌کند.
delivery settled           ack. گارد تکراری.
پیام نیست                  FAILED(PERMANENT)
منقضی شده                  FAILED(EXPIRED)
sender پیدا نشد            FAILED(NO_SENDER)
ارسال شد                   SENT با شناسهٔ provider
شکست دائمی                 FAILED(PERMANENT)
شکست گذرا، تلاش مانده      خطا، هیچ نوشتنی
شکست گذرا، آخرین تلاش      FAILED(MAX_ATTEMPTS)
```

## یک شکاف که موقع نوشتن بسته شد

`FailureMaxAttempts` تعریف شده بود ولی **هیچ‌کس نمی‌نوشتش**. طرح این بود که وقتی
JetStream از تلاش دست بکشد پیام به DLQ برود — ولی آن‌وقت هیچ ردیفی در دیتابیس
نمی‌گفت چه شد، و source هرگز نمی‌فهمید چرا پیامش نرسید.

حالا dispatcher می‌داند این آخرین شانس است و نتیجه را می‌نویسد، بعد ack می‌کند. DLQ
تور ایمنی می‌شود نه سازوکار اصلی.

## تفکیک خطای registry

اگر `SenderRegistry.For` شکست بخورد دو حالت کاملاً متفاوت است، و اشتباه‌گرفتنشان
یعنی یا تا ابد retry کردن چیزی که هرگز کار نمی‌کند، یا دور انداختن پیامی که فقط
دیتابیس یک لحظه در دسترس نبود.

```go
if errs.IsType(err, errs.ErrInvalidInput) {
    return d.fail(ctx, del, delivery.FailureNoSender, ...)   // پیکربندی
}
return err                                                    // خودِ lookup
```

با `errs.IsType` تفکیک شد نه با فهرست‌کردن sentinel ها، پس sentinel تازه در
`credential` این را نمی‌شکند.

## `ErrInvalidTransition` موفقیت است

اگر بین خواندن و نوشتن، worker دیگری همان delivery را بسته باشد، این خطا می‌آید. آن
پایان **مورد انتظار** یک event بازتحویل‌شده است نه یک شکست، پس به `nil` تبدیل
می‌شود.

# Follow-ups / Risks

- `maxAttempts` از config می‌آید ولی `internal/config` هنوز خالی است. باید با
  `MaxDeliver` استریم یکی باشد؛ اگر عدد ما بزرگ‌تر باشد، broker زودتر دست می‌کشد و
  آن ردیف هرگز `MAX_ATTEMPTS` نمی‌گیرد و `PENDING` می‌ماند تا sweep برش دارد.
- adapter نتس باید `NumDelivered` را از metadata بردارد و به `Handle` بدهد. این
  تنها جایی است که آن عدد در دسترس است.
- `RetryAfter` روی `SendError` هست ولی `Handle` استفاده‌اش نمی‌کند: با NAK ساده،
  backoff مال JetStream است. اگر بخواهیم به hint ارائه‌دهنده احترام بگذاریم،
  adapter باید `NakWithDelay` بزند و برای آن باید مقدار را از خطا بیرون بکشد.
