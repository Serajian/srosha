# Summary

`internal/adapter/alert` نوشته شد: یک صفِ کران‌دار، یک worker، و قانونی که کلِ
پکیج برایش وجود دارد — **اعلان هرگز نباید کاری را که خبرش را می‌دهد بلاک یا
خراب کند.** task یک از پنج در plan ــِ `2026-09-01-operator-alerts.md`.

spec و plan هم در همین commit می‌آیند، چون تا حالا commit نشده بودند.

`Notify` هیچ چیزی برنمی‌گرداند. خطایی نیست که صداکننده بتواند رویش کاری کند، و
برگرداندنش فقط کسی را وسوسه می‌کند که چکش کند.

`Pusher` را خودِ پکیج اعلام می‌کند نه اینکه import کند — یک adapter نمی‌تواند
adapter ــِ دیگری را import کند، و bootstrap تنها جایی است که هر دو را می‌بیند.
همان چیزی که پیامِ خطای `make arch-check` پیشنهاد می‌دهد.

pusher ــِ nil یعنی خاموش: نه صفی، نه goroutine ای. روی لپ‌تاپ کسی Gotify ندارد
و این نباید آنجا هزینه‌ای داشته باشد.

# دو چیزی که قدمِ «عمداً خرابش کن» پیدا کرد

plan اجبار می‌کند تستِ اصلی را عمداً قرمز کنی. هر دو بار چیزی گرفت.

**بارِ اول، ترتیبِ `defer` در خودِ تست غلط بود.** `Close` منتظرِ worker می‌ماند و
worker تا `release` بسته نشود گیر است — و آن `defer` بعد از `Close` اجرا می‌شد.
تست هنگ می‌کرد به‌جای اینکه بیفتد. حالا کامنتش می‌گوید چرا ترتیب مهم است.

**بارِ دوم، یک اشکالِ واقعی در کد.** شکست با `panic: send on closed channel`
آمد نه با پیامِ تست. دلیلش این بود که `Close` صف را می‌بست، و هر `Notify` ای که
هم‌زمان می‌رسید روی کانالِ بسته می‌نوشت و **پروسه panic می‌کرد** — از دلِ همان
کامپوننتی که کلِ کارش این است که هیچ‌وقت چیزی را نشکند.

کامنتِ خودم ادعا کرده بود `sync.Once` جلویش را می‌گیرد. نمی‌گرفت؛ فقط جلوی
بستنِ دوباره را می‌گرفت.

اصلاح: **صف هرگز بسته نمی‌شود.** یک کانالِ `stopped` جدا بسته می‌شود و worker با
`select` روی هر دو می‌ماند، بعد `drain` می‌کند و برمی‌گردد. نوشتن روی صف بعد از
Close بی‌خطر است — در بافر می‌ماند و کسی نمی‌خواندش، که در حالِ خاموش شدن درست
است.

بعد از اصلاح، دوباره خراب کردم و این بار پیامِ درست آمد:

```
--- FAIL: TestNotifyDoesNotBlockWhenTheQueueIsFull
    Notify blocked: a stuck push server would stall whatever called it
```
