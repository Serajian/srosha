# Summary

دو سند عوض شد و یک plan نوشته شد. **هیچ کدی تغییر نکرد.**

## تصمیمِ مالک

سه چیز، و هر سه جهتِ چیزی را برمی‌گردانند که در spec نوشته شده بود:

```
۱  sourceای که credential ندارد، از هویتِ پیش‌فرضِ srosha استفاده می‌کند
۲  خرید و طرح و پلن کلاً کنسل — srosha با همه یکسان رفتار می‌کند
۳  مرحلهٔ تأییدِ ادمین برمی‌گردد
```

## چرا این‌ها به هم وصل‌اند

spec یک قاعده داشت به اسمِ «قاعده‌ای که جای تأیید را گرفت»:
`sources.may_use_shared_sender` پیش‌فرض false، پس sourceای که چیزی ثبت نکرده
چیزی نمی‌فرستد. استدلالش این بود که هزینهٔ سوءاستفاده را روی خودِ سوءاستفاده‌کننده
می‌گذارد — اسپمر باید بات خودش را بیاورد و اسپم به اسمِ خودش امضا می‌شود.

آن قاعده روی دو ستون ایستاده بود و هر دو افتادند:

**فرستادن به‌عنوانِ srosha خودِ محصول است، نه بدهی.** sourceای که قبل از اولین
پیام باید بات ثبت کند، سخت‌ترین بخشِ راه‌اندازی را اول انجام می‌دهد. هویت‌های
پیش‌فرض همان چیزی‌اند که اولین پیام را ممکن می‌کنند، و برداشتنشان برای فیلترکردنِ
اسپمر، آن‌ها را از همه برمی‌دارد.

**توجیهش یک طرحِ پولی بود.** متنِ قبلی می‌گفت آن flag «همان چیزی می‌شود که یک
طرحِ پولی روشنش می‌کند». طرحی وجود ندارد. آن جمله را که برداری، قاعده تبدیل
می‌شود به مالیاتی دائمی روی هر مشتریِ سالم، برای اینکه یک گفت‌وگو با اپراتور
انجام نشود.

پس تأیید برگشت. یک آدم چند دقیقه وقت می‌گذارد، یک‌بار، و بعدش محصول برای هر کسی
که رد شده هیچ فرقی نمی‌کند.

## چیزی که موقعِ خواندنِ کد معلوم شد

**تأیید تقریباً مجانی است.** `sources.is_active` از قبل هست و از قبل هم گیت است:

```
source/auth.go:62     EnsureActive()  داخلِ Authenticate  ← کلید رد می‌شود
source/service.go:43  EnsureActive()  داخلِ Load          ← پیام رد می‌شود
```

پس چیزی برای ساختن نیست جز اینکه پیش‌فرضِ ستون `FALSE` شود و یک اپراتور بتواند
برش گرداند. `approved_at` هم اضافه می‌شود ولی **رکورد است نه گیت** — هیچ‌چیز
برای تصمیم‌گیری نمی‌خواندش؛ فقط صفِ بررسی می‌تواند بپرسد چه چیزی هرگز تأیید نشده،
بدونِ اینکه هر چیزی که ماهِ پیش خاموش شد هم در فهرست بیاید.

**و آن تصمیمِ بازِ spec با حذف بسته شد.** «`Registry.For` شناسهٔ source را
می‌گیرد و flag را نمی‌بیند» دیگر موضوعیت ندارد: وقتی fallback به هویتِ srosha
رفتارِ درست است، آن کد اصلاً دست نمی‌خورد.

## یک چیزی که spec جوابش را نداده بود

`Load` خودش `EnsureActive` را صدا می‌زند، و `Registrar.Register` و
`Credentials.Register` هر دو از `Load` رد می‌شوند. یعنی با sourceای که خاموش
ساخته می‌شود، مشتری **نمی‌تواند** برایش bot یا callback ثبت کند تا وقتی تأیید
شود.

نتیجه‌اش این می‌شد: ثبت کن، منتظر بمان، برگرد، پیکربندی کن، بفرست — و اپراتور
پوسته‌ای خالی را تأیید کند.

plan این را با جدا کردنِ دو مسیر حل می‌کند: `Load` مالِ مسیرِ فرستادن می‌ماند و
`Manage` اضافه می‌شود که ردیف را می‌خواند و فعال بودن را لازم ندارد. Task 2 است
و دلیلش همان‌جا نوشته شده.
