# Summary

**مستندِ SDK از وسط شروع می‌شد.**

`srosha.New(ctx, addr, apiKey)` را نشان می‌داد و **هرگز نمی‌گفت `apiKey` از کجا
می‌آید**. یک مشتری که آن را می‌خواند، در همان خطِ اول گیر می‌کرد.

بازنویسی شد — از جایی که مشتری واقعاً می‌ایستد — و یک نسخهٔ فارسی هم گرفت.

# و جوابِ آن سؤال، شرم‌آور است

```
Mint()  نوشته شده  ·  هیچ‌کس صدایش نمی‌زند
admin API  نیست  ·  CLI  نیست  ·  کنسول  نیست
```

**تنها راهِ وجود داشتنِ یک source، دو `INSERT` دستی است.** همان کاری که امروز
چهار بار کردم.

مستند این را می‌پوشاند یا صریح می‌گفت. صریح گفتنش را انتخاب کردم:

> You cannot mint one yourself, and there is no sign-up. srosha has no admin
> API and no console: whoever runs it creates your source and hands you a key
> out of band.

و زیرش، در یک `<details>` برای اپراتور، **دقیقاً همان دستوری که کار می‌کند** —
چون قایم کردنِ یک شکاف آن را پر نمی‌کند.

## یک چیزی که خودم سه بار به آن خوردم

بارِ اول شناسه‌ای با «O» ساختم و `ulid_check` ردش کرد. سومین بارِ امروز بود.

یعنی `<26-char ULID>` در مستند کافی نیست. حالا یک `mkid` واقعی می‌دهد، با این
جمله:

> Crockford base32, which EXCLUDES I, L, O and U. Typing one by hand and

# چه چیزی اضافه شد که نبود

```
۱  چه لازم داری، به چه ترتیب      آدرس، کلید، و (اختیاری) هویتِ فرستنده
۲  کلید از کجا                    و اینکه خودت نمی‌توانی
۴  کلِ پیام                        هر هفت فیلد، و اینکه فقط Body و Routes اجباری‌اند
۴  عنوان و متن در هر کانال         سه رفتارِ متفاوت
۴  شکل‌هایی که یک پیام می‌گیرد      یک نفر چند راه · چند نفر یک راه · From · To
۴  metadata که دو کانال می‌خوانند   template ــِ WhatsApp، data ــِ FCM، aps ــِ APNs
۴  «پذیرفته شد» یعنی چه           Submit وقتی ذخیره شد جواب می‌دهد، نه وقتی رسید
۵  Status و Reason، جدول‌بندی      و اینکه NotReachable تنها موردِ قابلِ اقدام است
۶  آدرسِ هر کانال، با نمونه        قبلاً هیچ‌جا نبود
۷  هر credential چه می‌خواهد       با تله‌هایش: PhoneNumberID شمارهٔ خودش نیست
۷  «یک بار» یعنی یک بار            و اگر در init بگذاری چه می‌شود
```

بخشِ ۶ شکافِ واقعی بود: مشتری از کجا می‌دانست Matrix اتاق می‌خواهد نه کاربر، یا
Telegram با `@name` فقط کانالِ عمومی را پیدا می‌کند؟ از هیچ‌جا.

## دو چیزی که فقط با خواندنِ کدِ ما می‌شد فهمید

**عنوان در هر کانال یک چیزِ متفاوت است.** برای email موضوعِ نامه است، برای FCM و
APNs فیلدِ جدا، و برای بقیه با یک خطِ خالی به متن چسبانده می‌شود.

**و `template` ــِ WhatsApp** — با کلیدهای دقیقش، پیش‌فرضِ `en_US`، و اینکه
`template_params` یک **آرایهٔ JSON** است نه رشته‌ای جداشده با کاما.

## و «یک بار» که آزموده شد، نه استدلال

صاحب پرسید اگر کسی `Register` را در init ــِ اپ بگذارد چه می‌شود. اجرا شد:

```
بارِ دوم با توکنِ متفاوت    →  ErrDuplicate، و توکنِ ذخیره‌شده عوض نشد
بارِ سوم با Default:false   →  ErrDuplicate، و پیش‌فرض همچنان true ماند
updated_at == created_at    →  سطر اصلاً لمس نشد
```

پس **مخرب نیست** — کلِ درخواست رد می‌شود نه اینکه نیمه‌کاره اعمال شود. ولی سه
پیامد دارد که نوشته شد: اپی که بعد از بارِ اول بالا نمی‌آید، رازی که مجبور است
برای همیشه در env بماند، و آن واگراییِ خاموش بعد از `Rotate` — کد فکر می‌کند
مالکِ توکن است و نیست.

و بحث شد که آیا SDK نباید خودش idempotent اش کند. **نه**، و دلیلش در مستند
نوشته شد: تنها راهش نادیده گرفتنِ رازی است که با ذخیره‌شده فرق دارد، و اصلاً
نمی‌تواند تشخیصش دهد چون srosha هرگز رازی برنمی‌گرداند. همان تلهٔ سوم، جابه‌جا
شده به جایی که دیدنش سخت‌تر است.

الگوی درست سه خط است و در مستند آمد — با این توضیح که `List` گرفتنِ قبلش بهتر
نیست، چون داور همان unique index است.

## و یک چیزِ کوچک که آزمایش نشانش داد

**نام‌ها به‌ازای هر کانال یکتا هستند، نه به‌ازای هر source.** `alerts` روی
telegram و `alerts` روی email دو هویتِ متفاوت‌اند. در مستند نبود.

## آدرس: مستند زیادی سخت‌گیر بود

نوشته بودم `host:port`. صاحب پرسید چرا پورت، و حق داشت. از خودِ gRPC پرسیده شد:

```
localhost          →  [::1]:443       ← پورت ندادی، ۴۴۳ فرض شد
localhost:50051    →  [::1]:50051
```

پس `api.srosha.dev` کار می‌کند و یعنی ۴۴۳ — دقیقاً همان چیزی که پشتِ Traefik
می‌خواهی. با پیش‌فرضِ TLS، **حالتِ رایج هیچ چیزِ اضافه‌ای نمی‌خواهد**.

و آن سطرِ داخلِ شبکه هم توضیح گرفت، چون سه چیزِ ناآشنا را با هم داشت:

```
gateway          نامِ سرویس در compose، حل‌شده با DNS ــِ خودِ Docker
:50051           لازم است چون پورت هرگز منتشر نمی‌شود -- فقط expose
WithInsecure()   چون TLS سرِ Traefik خاتمه می‌یابد
```

# Follow-ups / Risks

- **این شکاف با مستند بسته نشد، فقط اسمش نوشته شد.** srosha راهی برای ساختنِ
  source و کلید ندارد. یک زیرفرمانِ CLI روی `cmd/` کوچک‌ترین جوابِ ممکن است و
  `auth.Scheme.Mint()` از قبل نوشته و آمادهٔ صدا زدن است. تا آن روز، هر مشتریِ
  تازه یعنی کسی که به production ــِ postgres وصل می‌شود و `INSERT` می‌زند.
- **دو مستند می‌توانند از هم جدا بیفتند.** هیچ چیز هم‌ترازیشان را چک نمی‌کند.
- **نمونه‌کدهای داخلِ markdown کامپایل نمی‌شوند.** آن‌هایی که در
  `example_test.go` اند می‌شوند، ولی این‌ها نه.
- **رازِ امضای webhook هم بیرون از سرویس داده می‌شود** — همان جنسِ شکاف، برای
  همان دلیل: `NOTIF_WEBHOOK_SECRETS` یک متغیرِ محیطی است، پس هر مشتریِ تازه یک
  redeploy است. در `CONFIG.md` نوشته شده.

# آنچه در حینِ همین گفت‌وگو تصمیم گرفته شد و مرحلهٔ بعد است

**`Whoami`.** صاحب پرسید آیا SDK بهتر نیست یک `Ping` داشته باشد تا source بتواند
چک کند srosha بالاست و کلیدش درست است. جوابِ توافق‌شده: بله، ولی نه `Ping` —
یک rpc به نامِ `Whoami` که ضمنِ ثابت کردنِ بالا بودن، **دو شکافِ موجود را هم
می‌بندد**:

```
name · max_priority · custom_addresses · retention
```

امروز سقفِ اولویت را فقط وقتی می‌فهمی که `downgraded=true` بگیری، و مدتِ نگه‌داشت
را فقط وقتی که `List` رد شود.

ارزشش **زمانِ فهمیدن** است: `New` به هیچ‌کس وصل نمی‌شود، پس آدرسِ غلط یا کلیدِ
غلط سرِ اولین `Submit` معلوم می‌شود — که ممکن است ساعت‌ها بعد باشد، روی پیامی که
مهم بوده.

و یک چیزی که نباید بکنیم: `New` نباید خودش صدایش بزند. srosha ناهمگام است؛ اگر
لحظه‌ای پایین باشد، اپِ مشتری نباید بالا نیاید.

**روی این برنچ انجام نشد** — تغییرِ سرور است و مرحلهٔ بعد.
