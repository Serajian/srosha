# Summary

راهنماییِ «هر `$` را دوبل کن» که چند commit پیش نوشتم **غلط بود و امروز دو بار broker
را زمین زد**. با حقیقت عوض شد: هشِ bcrypt را عیناً همان‌طور که تولید می‌شود بگذار.
**هیچ کدی عوض نشده.**

## چه شد

با آن راهنمایی، مقدار به nats می‌رسید به‌شکلِ `$2a$$11$$...`. و nats وقتی مقداری با
`$` شروع شود، **دوباره** آن را یک ارجاعِ متغیر می‌بیند:

```
nats-server: variable reference for 'NATS_GATEWAY_PASSWORD' on line 129
  could not be parsed: variable reference for '$2a$$11$$xpoi...' on line 1
  can not be found
```

سرور crash-loop کرد. اپ نمی‌توانست بفرستد. برگشت با نوشتنِ دوبارهٔ رمزهای خام انجام
شد و بعد هشِ **بدونِ escape** امتحان شد: تمیز بالا آمد، بدونِ هشدارِ plaintext.

## چرا غلط نوشته شد

تست کرده بودم و تست هم واقعی بود — ولی **در محیطِ اشتباه**. با `docker compose` خالص
و یک `.env` دستی، compose واقعاً `${...}` را باز می‌کند و `$` ــِ escape نشده را
می‌خورد؛ اندازه گرفتم و دیدم کانتینر `$2a$11` می‌گیرد. آن مشاهده درست بود.

Dokploy این مقادیر را از آن مسیر به compose نمی‌دهد. پس آن آزمایش، رفتارِ چیزی را
اندازه گرفت که شبیهِ هدف بود، نه خودِ هدف — و نتیجه‌اش به‌عنوانِ دستورالعملِ هدف نوشته
شد.

این دقیقاً برعکسِ چیزی است که امروز چند بار درست انجام شد: دسترسی‌های nats با
`trace` روی همان کتابخانه‌ای اندازه گرفته شد که واقعاً اجرا می‌شود، و همان‌جا
`$JSC.CI.>` ای پیدا شد که هیچ استدلالی نمی‌یافتش. تفاوتِ این دو، اندازه‌گیری نیست —
اندازه‌گیریِ **چیزِ درست** است.

## آنچه جایش نشست

در هر سه جا: هش را همان‌طور که هست بگذار، `$` را دست نزن. و یک چکِ واحد که به‌جای
نگاه کردن به مقدار، نتیجه را می‌بیند:

```bash
docker logs <nats> | grep -iE 'plaintext|could not be parsed'
```

خالی درست است. `plaintext` یعنی رمزِ خام رفته تو؛ `could not be parsed` یعنی کسی
`$` ها را escape کرده.
