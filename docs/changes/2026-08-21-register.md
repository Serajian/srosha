# Summary

`register` نوشته شد: یک source می‌گوید نتیجهٔ ارسال‌هایش کجا push شود.
`webhook.Service` هم ساخته شد — آخرین aggregate ای که سرویس نداشت.

## `source.Load` در کنار `Admit`

**مشکل:** `Admit` سقف نرخ را چک می‌کند و یک واحد از سهمیه را **مصرف** می‌کند. آن
سهمیه برای فرستادن پیام است. اگر `register` هم صدایش بزند، مشتری‌ای که فقط آدرس
callback اش را عوض می‌کند، ظرفیت ارسال پیامش کم می‌شود.

**راه‌حل:** دو متد با دو سؤال متفاوت.

```go
Admit(ctx, id)   «آیا حق دارد بفرستد؟»   سقف نرخ + خواندن + فعال
Load(ctx, id)    «این source کیست؟»       خواندن + فعال
```

`Admit` حالا خودش `Load` را صدا می‌زند، پس چک فعال‌بودن یک بار نوشته شده. اسم‌ها
تفاوت را می‌گویند، پس اگر روزی کسی در مسیر ارسال `Load` بنویسد در review دیده
می‌شود.

## یک source، یک callback

`Register` اگر webhook نباشد می‌سازد، و اگر باشد **همان را جابه‌جا می‌کند**. برای این
کار `Webhook.Redirect` اضافه شد.

## و چیزی که موقع نوشتن `Redirect` مهم شد

اگر آدرس تازه بدون اعتبارسنجی نوشته می‌شد، کل کنترل SSRF از راه **به‌روزرسانی** دور
زده می‌شد:

```
ثبت اول:  https://acme.com/hooks    از چک رد می‌شود
ثبت دوم:  https://nats:8222/jsz     ← بدون چک، همین‌جا وارد می‌شد
```

پس اعتبارسنجی از `New` بیرون کشیده شد به یک `validate` مشترک که هر دو مسیر
صدایش می‌زنند، و یک تست همین را قفل می‌کند.

## آدرس تازه، شروع تازه

`Redirect` دوباره فعال می‌کند و شمارندهٔ شکست را صفر می‌کند. اگر endpoint قدیمی مرده
بود و ما خاموشش کرده بودیم، آن هیچ چیزی دربارهٔ آدرس تازه نمی‌گوید.

ولی `Deactivate` آدرس را نگه می‌دارد، پس روشن‌کردن دوباره ثبت مجدد نیست.

## راز امضا در config می‌ماند

مالک تصمیم گرفت هر source راز خودش را داشته باشد، در config، به‌صورت
`map[source]secret`.

پس `Register` هیچ رازی تولید نمی‌کند و برنمی‌گرداند. entity هم فیلدی برایش ندارد.
adapter موقع امضا از config می‌خواندش.

راز **جدا به ازای هر source** است نه یک راز مشترک: با یک راز واحد، هر source ای که
آن را دارد می‌تواند یک callback امضاشدهٔ معتبر به endpoint یک source دیگر بفرستد.
